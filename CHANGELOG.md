# Changelog

All notable changes to this project are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Repository scaffold: `Dagline` and `Dagline.Spectre` packages, tests, sample, docs site and CI.
- `GraphBuilder` builds a `Graph` of root-level tasks, each a `TaskBody` delegate, joined by `TaskNode.Requires`.
- `Runner.RunAsync` runs a graph to its end: each task goes pending, ready, running, succeeded in dependency order, ready tasks start on the thread pool in declaration order, and one built graph can be run any number of times.
- `RunOptions` with the required `Journal` choice (`Journal.None` is the only one so far), the run's `TimeProvider` and its `Reporters`.
- Limits and the cap: `Limit` on a task or a group names a limit, and `RunOptions.Limits` and `RunOptions.Cap` (16 by default) size them for one run. A running task holds one slot of the cap and of every limit named on it or on a group that holds it. Ready tasks are tried in declaration order at the start of the run and whenever a task settles: each takes all its slots at once or none, and one that does not fit is passed over without holding up the tasks behind it.
- `RunConfigurationException`, derived from the new base `DaglineException`: `Runner.RunAsync` throws it before anything happens when the cap or a size is below 1, or the graph names a limit that has no size. Its message lists every problem.
- `Snapshot.Cap` and `Snapshot.Limits` give the cap and each limit the graph names as a `LimitUse` (size and slots in use), and `NodeSnapshot.Limits` the limits named on a node.
- Docs: naming limits in the Defining a graph article, and sizing the cap and limits in the Running and stopping article.
- `RunResult` with the `RunOutcome` and the final `Snapshot`, and `RunOutcome.ToExitCode()` giving 0, 1 and 2 for complete, incomplete and stopped.
- `IReporter` receives `RunStarted`, every `TaskStatusChanged` and `RunEnded` in order, each with the `Snapshot` as of that event, and can read the run at any time through the `ISnapshotSource` on `RunStarted`.
- Reporter delivery guarantees: each reporter has its own unbounded queue and is called for one event at a time, the run never waits for a reporter while tasks are running, and at its end the run waits until every reporter still attached has handled every event.
- A reporter that throws, or whose returned `ValueTask` faults, is dropped while the run carries on, and `RunResult.ReporterErrors` has a `ReporterError` naming the reporter, the event and the exception.
- Docs: the Reporters article.
- `Snapshot` lists every node in declaration order as a `NodeSnapshot` (status, start and settle times, declared dependencies), finds a node by path, and counts tasks per `NodeStatus`.
- `NodePath`, the identity of a node, with `Parse`, `TryParse`, `Segments` and `Parent`.
- `TaskContext` gives a task body its `Path` and the run's `TimeProvider`.
- Docs: the Running and stopping article, the generated API reference in the site nav, and the glossary as a page of the site.
- Groups: `GraphBuilder.Group` and `GroupNode.Group` return a `GroupNode` that is also the scope for its children, so groups nest to any depth with plain loops. `Title` on a task or group gives it a readable name, carried to `NodeSnapshot.Title`.
- `After` beside `Requires`, on tasks and on groups, each taking one handle or a collection of handles. A dependency against a group covers every task beneath it, one declared on a group applies to every task beneath it, an empty group is met at once, both kinds on one upstream are treated as *requires*, and exact duplicates collapse.
- Declaration order is a depth-first walk of the tree with each group's children in the order added to that group. `Graph` is an `IReadOnlyList<Node>` in that order and finds a node by path with `TryGetNode`.
- Build validation: `GraphBuilder.Build` checks the whole graph and throws one `GraphException` (a `DaglineException`) whose `Problems` lists every `GraphProblem`: an invalid segment, a duplicate path, siblings that differ only by case, a handle from another builder, a node that depends on itself, a dependency between a node and its own ancestor or descendant, and a cycle with every dependency of it spelled out. Adding a node still returns a handle when its segment is invalid or already taken.
- A builder is single use: once `Build` has returned a graph, the builder and every handle it made throw `InvalidOperationException` from any call that would change the graph.
- Docs: build errors in the Defining a graph article.
- `NodeSnapshot.IsGroup`, a derived `Status` for a group, and `NodeSnapshot.Counts`: the tasks per status beneath a group. The `GroupSettled` event is published when the last task beneath a group settles, deepest group first.
- Docs: the Defining a graph article.
- An exception that escapes a task body, a cancellation exception included, fails that task as an unexpected failure and the run carries on: `NodeSnapshot.Failure` is `FailureKind.Unexpected`, `Message` is the exception's message, and `Detail` holds its type and stack trace. The run outcome is then incomplete.
- Blocking: every task that requires a failed task, directly, through a group or through a chain, becomes blocked at once and names the failed task in `NodeSnapshot.BlockedBy`. A blocked task has a settle time and no start time. *After* tasks and unrelated tasks still run, and a group settles failed when a task beneath it failed, or blocked when none failed and one is blocked.
- The order of events within one step is fixed: the settle, the tasks it blocks, the tasks it makes ready, the groups that settle (deepest first), then the tasks that start, each list in declaration order.
- `Snapshot.Failed` lists the failed tasks, and `Snapshot.Blocked` gives one `BlockedTasks` per failed task that blocked anything, with every task it blocked and the roots: the highest nodes whose every task it blocked.
- What a task reports, through its `TaskContext`: `Status` and `Count` set progress (status text, and a count with an optional total), which shows in the snapshot as `NodeSnapshot.StatusText`, `Count` and `Total`, is never an event, and is frozen when the task settles.
- `TaskContext.Warn` adds a warning that stays on the task whatever status it settles with, in `NodeSnapshot.Warnings`, and publishes the new `WarningAdded` event. `Snapshot.WarningCount` counts every warning of the run and `Snapshot.WithWarnings` lists the tasks that have any.
- `TaskContext.Message` and `TaskContext.Detail` set the message and add detail lines of a task's outcome, on a task that succeeds as well as one that fails. A line break in a message or a warning becomes a space, and text given as detail is split into one line per break.
- Reported failures: `throw context.Fail(message, detail)` ends a task failed with `FailureKind.Reported`. Once `Fail` has been called the task ends that way however its body ends. `Fail` returns the new `ReportedFailureException`, and one that the task's own `Fail` did not make is an unexpected failure.
- An unexpected failure now adds the exception's type and stack trace after any detail lines the task had already added.
- The volume limit: the first 100 warnings and the first 100 detail lines of a task are kept, and the rest are counted in `NodeSnapshot.WarningsOmitted` and `NodeSnapshot.DetailOmitted`. No `WarningAdded` is published for a warning that is not kept.
- `TaskContext.StatusOf` reads the status of a node the task depends on: an upstream declared on it or on a group that holds it, or any node beneath an upstream group.
- A `TaskContext` is safe to call from several threads at once, and changes nothing once its task has settled.
- Docs: the Writing tasks article.
- `PlainTextReporter` prints a run to a `TextWriter` the app hands it: a UTC-timestamped line when the run starts, when a task starts, succeeds or fails (with its duration and message, and a failed task's detail lines beneath it), when a task adds a warning, when a group settles (with its counts) and when the run ends. A task that becomes ready and progress are not printed.
- The plain-text reporter prints one line for consecutive blocked events with one cause, such as `blocked 2 tasks by checks/b`, and a line of counts one minute after the last line it printed, measured on its own `TimeProvider`, until the run ends.
- The plain-text reporter ends a run with a summary: the count of tasks per status, every failed task (kind, time, duration, progress, message, detail lines and what it blocked, named by roots) and every kept warning under its task. A section with nothing in it is left out.
- The plain-text reporter writes all the lines of one event with one call and never lets two of its writes overlap. It guards only its own writes: an app that writes to the same writer during a run shares a synchronized one, such as `Console.Out` or a `TextWriter.Synchronized` wrapper, to keep the lines of one event together. A writer that throws drops the reporter and stops its line of counts, and the error is on `RunResult.ReporterErrors`.
- `samples/Dagline.Samples.Basic` is a real run: one group, two tasks and a *requires*, printed by the plain-text reporter on standard output, with the run outcome mapped to the exit code.
- Docs: the plain-text reporter and its line formats in the Reporters article, and the Concepts article.
- The plain-text reporter prints the progress of a failed task on one line: a line break in the status text the task set becomes a space. `NodeSnapshot.StatusText` still holds the text as the task gave it.
- The event records `RunStarted`, `TaskStatusChanged`, `WarningAdded` and `GroupSettled`, and `ReporterError`, `BlockedTasks` and `GraphProblem`, reject a null argument with `ArgumentNullException`, both when one is made and when one is copied by a `with` expression.
- An exception that escapes a task body and whose own `Message` or `StackTrace` throws still fails only its task, and the run still ends. A message that throws or is `null` is replaced by the full name of the exception's type, and a stack trace that throws is left out of the detail lines.
- Stopping a run: `Runner.RunAsync` takes an optional `StopSignal`, which replaces the two-parameter form. `StopSignal.Request` is safe from any thread, never blocks and never throws, and `IsRequested` and `Requests` report what was asked. Dagline hooks no console or process signal.
- Once the first request is applied, the run publishes the new `StopRequested` event, starts nothing (*after* tasks included) and signals the new `TaskContext.CancellationToken` on every running task (the token is signalled in that step, so before `RunAsync` returns, and callbacks registered on it run on the thread pool without holding up the run), then waits for its running tasks to end. A signal already requested when the run starts stops it with nothing started, and a signal can be passed to a later run.
- A body that ends with any cancellation exception after a stop is `Cancelled`, keeping its message, detail lines, warnings and frozen progress. A reported failure still wins, and a body that returns or throws anything else keeps its real status. Cancelled never blocks: a task that requires it stays pending, and one after it becomes ready.
- The grace period: `RunOptions.GracePeriod` (30 seconds by default, measured on the run's `TimeProvider`) bounds the wait for running tasks after a stop, and a second request on the signal ends the wait at once. `TimeSpan.Zero` lets go at once and `Timeout.InfiniteTimeSpan` waits for the bodies to end. A grace period below zero, or above `uint.MaxValue - 1` milliseconds (about 49.7 days, the longest timer a `TimeProvider` can create), other than the unlimited value is one more problem in `RunConfigurationException`.
- When the wait ends with tasks still running, the new `StoppedWaiting` event is published with a `StoppedWaitingReason` (`SecondStop` or `GracePeriodOver`), then each task still running becomes cancelled in declaration order with the message `still running when the run stopped waiting`, and the run lets go of it: `RunAsync` returns while its body may still be running. Nothing such a body reports or does afterwards changes the run, and an exception it ends with is dropped.
- `Snapshot.Stop`, a `StopState` with the time of the stop, the grace period and the deadline (none when the grace period is unlimited), `Snapshot.Cancelled`, and `Snapshot.NeverReached` (the tasks left pending or ready once the run has ended). The run outcome is `Stopped` when a stop was applied and a task did not succeed, and `Complete` when every task succeeded despite it.
- A stop ends the wait for reporters at the end of a run: any request on the signal that the run did not apply, the first or a later one, drops each reporter still busy, and a request made just as the run ends is never lost. The token passed to the reporter's `OnEventAsync` is cancelled (before `RunAsync` returns, with callbacks registered on it run on the thread pool), its remaining events are discarded, `RunResult.ReporterErrors` has its `ReporterError` with an `OperationCanceledException`, and `RunAsync` returns without waiting for its call, even one that blocks its thread. Each reporter has a token of its own, so a reporter that had handled every event keeps an uncancelled token. The run outcome is unchanged.
- Waiting: `TaskContext.Waiting(text)` opens a waiting scope that marks a running task as idle until an external system changes. Reporters get a `WaitingChanged` event when the wait begins and when it ends, once each however many scopes overlap, and `NodeSnapshot.WaitingSince` and `NodeSnapshot.WaitingText` show the wait on the node while it lasts. Waiting is never a status: a waiting task is running and keeps its slots. A task that settles with a scope open ends its wait just before it settles.
- The wait helper: `TaskContext.WaitUntil(interval, check, text)` waits on an external system. It marks the task as waiting with the text, checks at once, then checks again one interval after each check ends, on the run's clock, until the check returns true. The check gets the context's cancellation token. A stop ends a delay at once and the helper throws the cancellation, so the task is cancelled; a token already signalled on entry throws without calling the check. An exception from the check is not caught: it fails the task, as a reported failure when it came from `Fail`. An interval of zero or less is refused at the call. No deadline, backoff or jitter.
- The plain-text reporter prints stops and waits: `waiting <path>: <text>` (or `waiting <path>` with no text) and `waited <path> for <duration>`; `stop requested: waiting up to <duration> for <n> running tasks` (without the duration when the grace period is unlimited); `stopped waiting: grace period over, <n> tasks still running` or `stopped waiting: second stop, ...`; and `cancelled <path> in <duration>` with the task's message, if any. A count of one is singular. The summary gains a `cancelled` section between the failures and the warnings, one entry per cancelled task in the shape of a failure without its kind; tasks never reached are counted as pending and ready and not listed.
- Docs: the new Waiting on external systems article, placed before Running and stopping in the navigation; stopping, the grace period and the second stop in the Running and stopping article; how a task ends once a stop has been requested, and a task the run has let go of, in the Writing tasks article; the stop and waiting events, the stop, cancelled and waiting members of the snapshot, a stop ending the wait for reporters and the new plain-text lines in the Reporters article; and stopping, the grace period, cancelled, waiting and working in the Concepts article.
- Journals: `Journal.New(directory, description)` starts a run on a new journal and `Journal.Continue(directory, id)` continues one. Nothing touches the disk until `Runner.RunAsync`, which creates the directory if it is missing and one file, `<id>.journal`, whose id is the UTC creation time on the run's clock as `yyyyMMddTHHmmssZ`, a hyphen and six random lowercase hex digits. The run records its start, each task's start and settle with its whole outcome, and its end, one JSON line each. A settle reaches the disk before any dependent starts and before its event is published, a failure and the tasks it blocks share one flush, and the run's end reaches the disk before `RunAsync` returns.
- A run that continues a journal keeps each task whose latest settle is a success as an earlier success: succeeded from the start with its message, detail lines, warnings and settle time, no start time, no event, and every dependency on it met. Every other task starts pending and runs. A group made only of earlier successes is settled from the start and gets no event, and the run outcome counts earlier successes as succeeded. A continuing run may use a different cap and limit sizes.
- `Snapshot.Journal`, a `JournalInfo` with the journal's id, description and run number (from 1), `Snapshot.EarlierSuccesses`, `NodeSnapshot.IsEarlierSuccess` and `NodeSnapshot.EarlierSuccesses`, and `GroupSettled.EarlierSuccesses`, which counts a settling group's earlier successes apart.
- Set-asides: a continuing run keeps the earlier success of a task that is *after* something only when every node it is after is itself an earlier success in this run, an empty group included. Otherwise the success is set aside: the task starts pending and runs again, its path is in the new `Snapshot.SetAside` (declaration order), and the set-aside is written to the journal with the run's start, on disk before any task starts, so it holds in later runs until the task succeeds again. The rule spreads through *after* dependencies and never through *requires*.
- A graph that differs from its journal is never an error: a path in the graph and not in the journal is an ordinary pending task, and a journal path that is not a task of the graph (gone, or now a group) is left untouched and is not part of the run. `Snapshot.JournalPathsNotInGraph` counts those paths and `Snapshot.JournalPathsNotInGraphUnsucceeded` those of them with no success on record or whose success was set aside.
- `JournalNotFoundException`, a `DaglineException`: `RunAsync` throws it before the run exists when `Journal.Continue` names a journal that is not in its directory. An id not in the id format is refused by `Journal.Continue` with `ArgumentException`.
- Docs: the new Journals article, after Running and stopping in the navigation; the journal option and `JournalNotFoundException` in the Running and stopping article. ADR 0007's id example now matches the id format.
- Docs: the *after* rule and the two journal-path counts in the Journals article, and the new Running part of the work article, after Journals in the navigation.
- Checkpoints: `TaskContext.Checkpoint`, `TaskContext.SaveCheckpointAsync` and `TaskContext.ClearCheckpointAsync`. A task saves a piece of text of at most 4,096 bytes as UTF-8 (a longer one is refused at the call with `ArgumentException`), and the save completes once the text is flushed to the disk. A run that continues the journal hands it back when the task runs again. It is kept through a failure, a cancellation and a killed process, and discarded when the task succeeds. Saving again replaces it, saving an empty string or clearing removes it, and clearing when there is none writes nothing. The token cancels only a save that has not begun to write. A save during the grace period succeeds, and one after the task has settled or the run has let go of it throws `InvalidOperationException`. A checkpoint is in no event and no snapshot, and with `Journal.None` it lives in memory for the run.
- Docs: checkpoints, trigger-or-re-attach, clearing a checkpoint for a fresh start and the window between a start and its save in the Waiting on external systems article, and checkpoints in the Writing tasks article.
- A run holds its journal through a lock file beside it, `<id>.lock`, for its whole life, and lets go of it when the run ends, however it ends. `RunAsync` throws the new `JournalInUseException` before the run exists when another run, in this process or another, holds the journal. The lock file stays behind and holds nothing.
- `JournalOpenException` when a journal, its lock file or its directory cannot be opened, created or read, and `JournalFormatException`, with the format `Version` when there is one, when a file's first line is not a journal header, its version is unknown, or a line other than the last is not an entry. `RunAsync` checks the options, then the lock, then opens and reads the journal, each failure thrown before the run exists.
- `Journals.ListAsync(directory)` summarises every journal in a directory, oldest first, without a graph, and gives an empty list for a directory that does not exist. Each `JournalSummary` has the id, creation time, description, number of runs, the latest run as a `JournalRunSummary` (start, end, user, machine), how it ended as a `JournalEnding` (complete, incomplete, stopped, in use, died), whether the journal is finished, and `Counts` of the paths it records by last recorded status. A journal in an unknown format makes it throw `JournalFormatException` naming the file.
- `Journals.DeleteAsync(directory, id)` removes a journal and its lock file. Its returned task faults with `JournalInUseException` while a run holds the journal and `JournalNotFoundException` when it is not there, and the call itself refuses an id not in the id format.
- Docs: choosing a journal with `ListAsync`, the endings, holding, deleting and the journal exceptions in the Journals article; the journal exceptions in the Running and stopping article.
- After a killed process a journal always opens: a final line cut short is dropped, and the file is trimmed to the end of its last whole line before the continuing run appends. Every success and checkpoint whose line was whole is kept and everything else runs, a task that was running included, with its checkpoint. The listing drops such a line without changing the file. A new journal's directory entry, and that of each directory created for it, is flushed too on Unix systems, before any task starts.
- When a journal write fails during a run, Dagline stops the run itself: `StopRequested` is published with `By` set to the new `StopRequester.Dagline` (unless a stop was in progress), nothing new starts, running tasks are signalled and the run waits the grace period, which any request on the app's signal ends. Nothing more is written. The run ends with the new `JournalWriteException`, a `DaglineException` carrying the final `Snapshot` and the cause as its inner exception: `RunEnded` carries it in `Error` with no run outcome, and `RunAsync` throws it once reporters have handled every event. A checkpoint save that fails, or comes after a failed write, throws it to the task. A write the file system refuses for lack of permission (`UnauthorizedAccessException`) is a failed write as much as an `IOException` is. `StopRequested` gains `By`, and `RunEnded` gains `Error` with `Outcome` now nullable: exactly one is set, and an ordinary run still carries its run outcome. Both are set only by the constructor, so a `with` expression cannot change either.
- Docs: what is promised after a crash and a journal write that fails in the Journals article, and a journal write that fails in the Running and stopping article. ADR 0009 says a task the failing step had already started still starts and is signalled at once.
- The plain-text reporter on a journal: the `run started` line goes on with the earlier successes, the set-asides and the journal paths not in the graph with those not succeeded in brackets, each only when it is not zero, and is followed by `journal <id> run <n>: <description>` (ending after the number with no description). The summary begins with `journal:` and the same text. Wherever counts are listed, succeeded shows its earlier successes in brackets, as in `3 succeeded (1 earlier)`. The warnings count covers every task in the graph, only warnings added in this run are listed, and those of earlier successes are one line: `from earlier runs, not listed again: <n> on <m> tasks`. After the warnings come `left for a later run: <n> tasks`, `set aside: <n>` with each path, and `journal paths not in graph: <n> (<m> not succeeded)`, each only when it applies. A run with no journal prints exactly what it did before.
- The plain-text reporter prints a stop Dagline asked for as `stop requested by Dagline, journal write failed: ` followed by the usual text, and a run that ended with an error as `run ended: journal write failed after <duration>: <message>`, with the message of the cause, followed by the summary.
- Docs: the journal members of the snapshot, `GroupSettled.EarlierSuccesses`, the changed stop and end events and the new plain-text lines in the Reporters article, and journals, continuing, earlier successes, finished, descriptions and checkpoints in the Concepts article.
- `Dagline.Spectre`: `SpectreReporter.Auto(plainText, options)` gives the display, a reporter that draws a run on the terminal's alternate screen, and `SpectreOptions` (`Display`, `Ascii`, `Console`, `TimeProvider`) with `DisplayMode` (`Auto`, `Force`, `Never`). For now the display is always used, and the glyphs are the Unicode set.
- The display enters the alternate screen and hides the cursor on `RunStarted`, draws a first frame, then draws a new frame four times a second on the options' clock from the run's snapshot source, so a change no event carried shows in the next frame. A frame is cut to the console's width and height, which are read again for every frame. On `RunEnded` it stops drawing, leaves the alternate screen, shows the cursor and prints the summary on the ordinary screen. Its drawing is serialised.
- The frame's header: the journal's description, id and run number (or `no journal`), the percentage of tasks settled and the elapsed time; one bar for the whole run split by status; and a count per status, with working and waiting tasks apart, earlier successes in brackets and the warning count, then the cap in use over its size, how many limits are full and how many ready tasks are held. Zero counts are left out.
- The frame's working pane: its title carries the number of running tasks that are working, and it lists them in declaration order, each with its path, a progress bar and `n of m` (the count alone when there is no total, neither when there is no count), its status text and how long it has been running, ending with `and N more working` when they do not all fit. When every running task is waiting, the pane says so in one line.
- The frame's waiting pane, shown only while a task is waiting: its title carries the number waiting and the longest wait, and it lists up to five tasks, longest wait first, each with its path, its status text or else its waiting text, and how long it has waited, ending with `and N more, the newest waiting <duration>` when some are left out. Status text and waiting text are drawn on one line, each line break as a space.
- The frame's problems pane: a title with the failed, cancelled and warning counts and how many tasks are blocked behind how many failures; each failure, newest first, with how many tasks it blocks and when it failed (UTC), then its message; the cancelled tasks, newest first; and the latest three warnings, chosen by the order their `WarningAdded` events came. The pane takes no lines when there is nothing to show.
- The frame's stop banner: once a stop has been applied, one line under the header with how many running tasks the run is waiting for, the time left until the deadline (left out for an unlimited grace period) and `Ctrl+C again to stop waiting`. When Dagline asked for the stop, it says that the journal could not be written and that Ctrl+C stops waiting.
- The summary's first lines: a rule, the run outcome with its duration and the journal's id and run number, and the count per status with earlier successes apart and the warning count. No exit code is printed.
- The summary in full, each part after a blank line and left out when it has nothing to show: for a run that ended with an error, the error's message in place of a run outcome; how many tasks were not reached; every failed task in declaration order with its kind, the time it failed, how long it ran and how far it got (status text on one line), its message, its detail lines and how many were not kept, and what it blocked, named by the roots of the cascade with the number of tasks beneath a root that is a group; every cancelled task with its message; the warnings, with the total and how many tasks have any, each task with warnings added in this run with its kept warnings and how many were not kept, and one line for the warnings on earlier successes; and for a run with a journal, how many tasks a run that continues it has left, the earlier successes set aside, and the journal paths not in the graph with those not succeeded.
- The frame's groups pane, under the header: one row per group two levels down and per top-level node with no group beneath it, in declaration order, or one row per top-level node when those do not fit. A row is the node's status glyph, its title or else its last segment, one cell per child in the glyph and colour of its status (a group's derived status, drawn as waiting when all its running tasks are waiting, and an earlier success as a dimmer tick), then succeeded over total, the failures and the warnings. A row with more children than cells shows a bar split by status instead. A graph with no nodes has no groups pane.
